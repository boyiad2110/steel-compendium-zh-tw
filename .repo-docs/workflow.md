# 批次、本地驗收與發布

## 一批的工作流程

1. **確認範圍與分支**：在 [批次紀錄](batches/README.md) 列出玩家可完成的選擇、包含／不包含內容、必要依賴、預計頁面及驗收項目，從最新 `develop` 建立獨立 `codex/` 工作分支。使用者已同意的範圍直接執行，不重複詢問。
2. **整理譯文**：先沿用符合條件的核准內容。差異與缺譯整理成待審項目；需要新核准時依 [翻譯規則](translation.md) 處理，不能用工程完成取代翻譯核准。
3. **實作與驗證**：在顯示層接入，檢查適用位置與原功能，保留英文回退及原因。依 [開發文件](development.md) 執行相應驗證。
4. **建立批次 PR**：提交並推送工作分支，開啟目標為 `develop` 的 Draft PR。每批一個 PR，包含治理文件與上游同步；PR 與批次檔互相連結，列出範圍、驗證及人工驗收狀態。修正維持在原 PR，不直接推送至 `develop`。
5. **引導本地驗收**：確認本地正在預覽 PR 的指定版本，啟動預覽並提供可直接開啟的頁面、逐項操作與預期結果，列出剩餘英文及已知問題，讓使用者可依步驟確認。純文件批次改提供本地檔案與閱讀檢查點，不必啟動網站。
6. **等待使用者驗收**：清楚記為「待人工驗收」，PR 保持 Draft，禁止先合併或啟用自動合併。使用者提出修改時，在同一批與 PR 修正，重新交付受影響項目；明確通過後才進入收尾。
7. **收尾與合併**：記錄驗收日期、使用者確認摘要及已驗收 commit，將驗收紀錄補進原 PR；確認最新版本檢查通過及差異符合驗收範圍，再將 PR 轉為可審查並合併至 `develop`，預設 squash 合併並刪除遠端工作分支。更新本地 `develop`，在 PR 保留合併結果與批次關聯，才開始下一批。使用者驗收通過即允許依此流程收尾，不再重複詢問是否合併；另有暫緩指示時依指示處理。

簡單修正不必再拆新批或建立複雜審批。若發現新的必要依賴，先完成不受影響的工作，列出新增範圍及原因；跨出已同意範圍時取得使用者意見，不自行擴大到其他書籍或工具。

## 每批交付內容

- 範圍、實際變更、對應的 SC Master 紀錄 ID 或明確範圍。
- 對應 PR、工作分支、目標 `develop`、PR head commit 與本地驗收版本。
- 本地預覽啟動方式、網址、驗收頁面與步驟；若預覽未在執行，明確說明。
- 工程／核准／人工驗收各自狀態，及缺譯、原文差異、連結適配、顯示接線等英文殘留原因。
- 實際執行的檢查、結果與限制。自動產生的完整報告留在 `reports/`；追蹤在 Git 的批次檔保留必要摘要。

### 網站批次驗收清單

- 玩家能理解並完成本批涵蓋的選擇，名稱、說明、條件、成本、數值標籤及必要引用齊全。
- 適用的閱讀頁、瀏覽頁、內嵌卡片呈現一致；原連結、SCC 及錨點到達正確資料。
- 中文與英文名稱均能搜尋；適用的 Markdown／PNG 匯出與頁面一致。
- 相關擲骰、計算、收藏與分享功能維持原行為；站內即時導覽後仍可操作。
- 桌面／手機、明亮／深色模式沒有文字截斷、重疊或操作障礙。
- 不在本批內的內容保留原頁面及功能，缺譯維持英文並有說明。

不適用的項目寫明理由，例如純治理文件批次不需要卡片匯出或畫面測試。不得勾選尚未實際檢查的項目。

## 狀態及驗收證據

工程使用「未開始／進行中／待修正／完成」；譯文使用「未盤點／部分核准／全部核准／不適用」；人工驗收使用「未交付／待驗收／需修改／通過」。這些是批次摘要，不另造一套翻譯紀錄狀態去取代 Master 的狀態。

使用者的確認應對應批次、PR 與已提交版本；交付人工驗收前先提交並推送，記錄 PR head commit，確認本地預覽使用同一版本且沒有未列明的工作目錄修改。記錄日期及確認文字摘要，不得用稍後已改動的版本冒充先前驗收版本。

驗收後只補日期、確認摘要、PR 關聯等紀錄，不視為內容重新變更；仍須確認最新 PR 檢查通過。若新增程式、譯文、規則或畫面修改，必須重驗受影響項目，不能用先前確認直接合併。

通過後若改動已驗收內容，將受影響項目恢復待驗收並說明；無關頁面不需一律重審。「部分內容已核准」可以支援工程先行，但必要文字仍缺譯時，不標記該範圍中文化完成。

治理批次以 GOV 編號、CI 工程批次以 CI 編號、內容批次從 B01 起。詳見 [批次清單](batches/README.md)。GOV-01 是本規則生效前已驗收並直接整合的歷史批次，不補建無差異 PR；GOV-02 起每批都適用 PR 流程。分支策略及驗證分流見 [development.md](development.md)；推送或合併不表示可部署。

## 發布與部署

預設累積本地已驗收批次，**使用者明確指定要發布的批次／版本後才部署**。明確要求發布目前版本且範圍清楚時即為授權，不另外重複確認。以前的部署授權不延用到之後的批次。

發布前：

1. 列出本次要發布的批次、已驗收版本、剩餘英文及使用者發布指示。
2. 確認發布 commit 沒混入未驗收變更；若有未驗收工作，用對應的已驗收 commit 建置。
3. 用實際發布 URL 建置並完成驗證，檢查 canonical、SCC、分享連結與路徑前綴。
4. 才可手動觸發中文工作流程的部署；發布後抽查關鍵頁面，記錄 commit、工作流程連結與結果。

commit、push、PR、CI 成功及畫面驗收都不是部署授權。上游同步即使程式驗證通過，也需重驗受影響內容，不能自動發布。

目前 CI 的 `deploy` 預設為 `false`，沒有自動判讀使用者驗收或發布授權的功能；上述閘門由執行者與批次紀錄遵守，不能宣稱是程式強制控管。

## 族裔批次的盤點與紀錄

開始前使用[批次範本](batches/_template.md)盤點整個族裔頁面的規則、介紹、敘事故事及必要 UI／直接引用，逐項標示包含或排除及來源狀態；排除內容也列出英文位置。創角選擇可完成與整頁已中文化須分別陳述，不因盤點發現定稿就自行擴張授權。

交付前填寫適用呈現位置的實際結果，將自動檢查、Agent 瀏覽器檢查、使用者驗收分開；未執行寫明限制，不以測試通過或使用者總體通過補成 Agent 已檢查。每個修正列受影響頁、預覽版本及重驗步驟，保留無關項目的既有驗收。

批次頂部維護唯一現況摘要：目前範圍、最新程式／譯文版本、預覽版本與服務、譯文核准、人工驗收、CI／合併連結及限制。歷史紀錄保留日期與版本，明確標示被後續結果取代；PR 說明同步更新。合併結果可留在 PR 收尾留言並提供確切連結。後續族裔可參考 [B01 檢討](b01-retrospective.md)，不需載入全部舊排障過程。
